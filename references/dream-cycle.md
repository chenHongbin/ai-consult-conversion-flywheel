# 咨询转化 Dream Cycle（v1.6）

## 核心循环

咨询 Skill 的持续迭代不是“把更多录音塞进模型”，而是一个可回溯的学习飞轮：

```text
新增资料
→ 识别与去重
→ 长图切片/OCR、录音转写、HTML/PDF/Office 文本提取
→ 质量分层与失败记录（单条失败不阻塞整批）
→ 案例标准化
→ 正向样本/反例/待确认分组
→ 批量分析与对照蒸馏
→ 生成咨询能力候选 + 机构知识候选 + 患者洞察候选
→ 固定测试集回归
→ 影子试用代表案例
→ 三类运行时组件绑定为一个原子发布版本
→ 日常反馈回流
```

每轮都保留原始证据、处理清单、候选规则、测试结果和版本差异。不能因为一次批量处理成功就自动覆盖当前能力包。

外部资料的生命周期必须独立于 Skill：外部知识库、录音、聊天记录和图片是“用户本轮主动接入的输入”，不是默认记忆。它们不得被复制进 Skill 源码、通用参考资料或发布包；如需沉淀，只能在完成授权、脱敏、去机构化和用户明确纳入后，提炼为当前机构的抽象规则。

## 两种资料源

### 本地文件夹

首次初始化时由 `scripts/init_consult_workspace.py` 在用户指定的工作空间根目录下创建：

```text
咨询转化工作区/
├── 01_机构介绍/               用户放机构资料
├── 02_科室项目与服务/         用户放科室、项目和服务事实
├── 03_咨询流程与标准/         用户放 SOP、合规和流程
├── 04_优秀咨询案例/           用户放优秀录音和聊天
├── 05_普通失败与未预约案例/   用户放对照案例
├── 06_团队培训与反馈/         用户放培训、练习和复盘
├── 07_我的产出/               Skill 输出分析、话术、洞察和报告
├── 08_团队管理/               单主管团队、成员档案、会议、报表和自动化
└── _系统/                     Skill 自动维护处理过程和版本
```

用户不需要理解 `_系统`。转写、OCR、案例标准化、蒸馏候选、评估集和失败记录均在 `_系统` 中按子目录维护。

### IMA 知识库

使用 IMA 时记录知识库名称、科室/病种范围和同步文件夹。优先增量读取新文件，不重复下载全部内容。IMA 的限频、权限和笔记作者限制必须写入同步记录；失败条目进入 `_系统/失败记录/`，不影响其他条目继续处理。

## 批量蒸馏的五个阶段

1. **扫描**：生成文件清单、媒体类型、路径、哈希和新增/变更状态；
2. **标准化**：音频用 YouNavi 转写，长图先切片再 OCR，HTML/文档转成可检索文本；
3. **标注**：识别科室、病种、渠道、咨询阶段、结果标签、来源性质和授权状态；路径里的“已到/未到”只能作为待确认的结果线索；
4. **三层蒸馏**：批量对照优秀、普通、失败和高风险案例，提取行为—条件—效果；同时提取机构、科室、项目、医生、优势、资质和脱敏案例知识；再提取群体级患者决策状态和疑义意图，不摘录孤立金句；
5. **质量与覆盖率**：所有派生文本通过 manifest 回链原始录音、图片或文档；OCR 低质量文本降低证据权重，转写/提取失败写入失败清单但不阻塞其他材料；
6. **写回与影子试用**：让蒸馏 Agent 输出 `candidate.json`、`knowledge-candidate.json` 和 `patient-insight-candidate.json`，分别写入三类候选版本；对代表性的正向、反向、对照和未知案例自动生成八步法影子复盘，先验证可用性，不要求先补齐全部机构事实；
7. **统一发布**：固定测试、事实确认、冲突检查和隐私审核通过后，使用 `scripts/publish_release.py` 把三类 active 组件绑定为同一个 release；团队包只从这个 release 构建；
8. **运行与反馈**：日常分析读取统一 release 绑定的三类运行时；管理者的“保留/修改/废弃”反馈进入对应队列，进入下一轮增量蒸馏。患者洞察只作为当前对话的待验证假设，陪练使用合成场景。

## 每轮蒸馏的输出

每轮至少生成：

- `batch-manifest.jsonl`：本轮处理的案例清单；
- `distillation-candidates.md`：候选咨询动作、话术、流程和风险规则；
- `evidence-map.jsonl`：候选规则对应的案例和时间点/OCR位置；
- `review-queue.md`：科室、结果、授权、事实和合规待确认项；
- `knowledge-candidate.json`：机构介绍、科室项目、医生、优势、资质和案例知识候选；
- `knowledge-review-queue.md`：待确认、冲突、过期和被拒绝知识；
- `patient-insight-candidate.json`：决策状态、疑义意图和合成陪练候选；
- `patient-insight-review-queue.md`：证据、反例、去重簇、隐私和管理者审核队列；
- `eval-report.md`：固定测试集结果、回归失败和版本差异。

团队管理的结果反馈单独保留：每周生成员工管理报告，每月把一对一沟通与近四周过程量、结果数据合并复盘。员工管理报告只用于支持和改进行动，不自动写入绩效定级，也不能反向污染机构咨询能力包。

## 发布策略

自动处理可以自动生成候选版本。影子试用用于先发现“报告是否能跑、证据是否够、事实是否缺失”，不等于自动发布。通过覆盖率、证据、反例、隐私、医疗边界和固定测试后，使用 `scripts/publish_release.py` 原子切换三类运行时；失败时不影响旧版本。用户不需要理解版本号；如果用户说“回滚上一版”，使用 `scripts/rollback_release.py` 同步改变三类组件和统一 release 指针，不删除任何资料。

## 周期运行

Skill 提供可重复执行的批处理脚本，但 Skill 本身不应偷偷创建系统定时任务。用户可以用 WorkBuddy 的定时能力、系统任务或手动触发：

```text
首次运行：扫描当前工作空间根目录的全部候选资料 → 完成全量转写/OCR/标准化 → 通过覆盖率闸门后生成候选蒸馏报告。

后续每周六：扫描当前工作空间根目录 → 按文件哈希只处理新增或变化资料 → 生成候选蒸馏报告 → 输出待发布提示。
```

周期任务只处理新增/变更文件，依据哈希去重；遇到权限、脱敏、OCR、转写或文档提取失败，只记录失败并继续其他资料。夜间任务完成处理后可以生成影子复盘，但不得绕过审核自动发布团队包。
